# TTG-676211 — Lifetime Cap у Frequency Cap (Partner Offer Name)

## Бізнес-рекомендації щодо впровадження Lifetime Cap у налаштуваннях Frequency Cap

## 1. Мета рішення
Мета даного рішення — додати в налаштування `Frequency Cap` новий режим `LIFETIME`, щоб CPC-адвертайзери з prepay-бюджетами могли встановлювати тотальний ліміт кліків на рівні `Partner Offer Name`.

Рішення повинно:
- забезпечити контроль сумарної кількості кліків на весь життєвий цикл оферу;
- зменшити ризик перевищення узгодженого prepay-бюджету;
- зберегти існуючий UX блоку `Frequency Cap` із мінімальними змінами.

## 2. Загальний принцип рішення
Поточний блок `Frequency Cap` підтримує періодичність `DAILY` і `HOURLY`.  
У межах задачі додається третій режим `LIFETIME`, у якому:
- `Global Cap` трактуються як загальний ліміт на весь час;
- авто-скидання ліміту за календарним циклом не виконується;
- (опційно) доступна ручна дія `Reset` для Lifetime-режиму.

## 3. Схема роботи налаштування
Основні зони UI:
1. Toggle `Frequency Cap` (ON/OFF).
2. Поле `Global Cap`.
3. Правий оверлей у полі:
   - червоні лічильники (приклад: `473 471`);
   - іконка `Edit` (олівець);
   - іконка `Reset` (тільки в `LIFETIME`).
4. Група періодичності: `[DAILY | HOURLY | LIFETIME]`.
5. Група дії: `[EXCLUDE | RETURN]`.

## 4. Покроковий бізнес-потік
### Як це працює (короткий флоу)
1. Користувач відкриває налаштування оферу.
2. Увімкнює `Frequency Cap`.
3. Вводить значення в `Global Cap`.
4. Обирає режим періодичності (`DAILY/HOURLY/LIFETIME`).
5. Обирає дію при досягненні ліміту (`EXCLUDE/RETURN`).
6. Для `LIFETIME` (за потреби) виконує ручний `Reset`.

### Деталізація по режимах
**DAILY**
- ліміт застосовується в межах доби;
- reset відбувається за добовим циклом.

**HOURLY**
- ліміт застосовується в межах години;
- reset відбувається за погодинним циклом.

**LIFETIME**
- ліміт застосовується на весь період життя оферу;
- автоматичний reset відсутній;
- ручний reset доступний через іконку `Reset` (якщо увімкнено цей функціонал).

## 5. Перехід на оффер / вплив на воронку
Зміна не додає нових кроків у користувацький флоу кінцевого юзера та не ускладнює воронку.  
Вплив відбувається на рівні керування трафіком і бюджетом:
- точніший контроль prepay-кампаній;
- менше перевитрати кліків;
- прозоріша операційна логіка для менеджерів.

## 6. Функціональні вимоги
1. У блоці `Frequency Cap` доступні 3 режими: `DAILY`, `HOURLY`, `LIFETIME`.
2. `Global Cap` видимий у всіх режимах.
3. Стилізація `LIFETIME` ідентична іншим кнопкам групи:
   - active: синій стан;
   - inactive: сірий стан.
4. Іконка `Reset` відображається тільки для `LIFETIME`.
5. Іконка `Edit` відображається у всіх режимах.
6. При `Frequency Cap = OFF` всі контроли блоку переходять у disabled-state.

## 7. Acceptance Criteria
1. Кнопки періодичності: `[DAILY | HOURLY | LIFETIME]` відображаються коректно.
2. При виборі `LIFETIME` поле `Global Cap` не зникає.
3. У режимі `LIFETIME` є іконка `Reset`; у `DAILY/HOURLY` її немає.
4. `LIFETIME` має таку саму візуальну поведінку active/inactive, як інші режими.
5. При вимкненому toggle всі елементи блоку неактивні.
