# TTG-676211 — Frequency Cap: додати режим `LIFETIME`

## 1) Контекст
Частина CPC-адвертайзерів працює по prepay-моделі та запускає кампанії на фіксований бюджет, що напряму відповідає фіксованій кількості кліків.  
Поточні режими капування (`DAILY`, `HOURLY`) не покривають сценарій "загальний ліміт на весь період оферу".

## 2) Бізнес-проблема
- Немає можливості встановити **тотальну капу** (non-reset cap) на рівні `Partner Offer Name`.
- Через це кампанія може перевищувати погоджений обсяг кліків у рамках prepay-бюджету.

## 3) Бізнес-ціль
Додати в налаштування `Frequency Cap` новий режим періодичності **`LIFETIME`**, який трактує `Global Cap` як ліміт "на весь час" для конкретного `Partner Offer Name`.

## 4) Scope
### In scope
1. Оновлення UI-блоку `Frequency Cap`:
   - Перемикач `Frequency Cap` (on/off) залишається.
   - Поле `Global Cap` залишається видимим.
   - Додати третю кнопку періодичності: `LIFETIME`.
2. Візуальна та поведінкова логіка:
   - Група періодичності: `[DAILY | HOURLY | LIFETIME]`.
   - Група дії: `[EXCLUDE | RETURN]`.
   - Для `LIFETIME` показувати іконку `Reset` (опційна поведінка згідно задачі).
3. Поведінка ліміту:
   - У режимі `LIFETIME` значення `Global Cap` не має автоматичного reset за часом.

### Out of scope
- Зміни в білінгу/фінансових розрахунках.
- Розширена аналітика та нові звіти.
- Масова міграція історичних оферів (окрема задача, якщо потрібна).

## 5) Основні визначення
- **Global Cap** — максимально дозволена кількість кліків для обраного контексту.
- **LIFETIME Cap** — капа без авто-скидання по годинах/днях.
- **Partner Offer Name** — рівень, на якому застосовується total cap за цією задачею.

## 6) User stories
1. Як менеджер кампанії, я хочу обрати `LIFETIME`, щоб обмежити сумарну кількість кліків на весь цикл оферу.
2. Як менеджер кампанії, я хочу бачити поточні лічильники в полі `Global Cap`, щоб контролювати фактичне споживання.
3. Як менеджер кампанії, я хочу вручну скинути lifetime-ліміт через `Reset`, коли починається новий комерційний цикл.

## 7) Функціональні вимоги
1. В UI періодичності доступні 3 опції:
   - `DAILY`
   - `HOURLY`
   - `LIFETIME`
2. `Global Cap`:
   - Видимий у всіх 3 режимах.
   - Приймає тільки числове значення (ціле, > 0).
3. Іконки праворуч у полі:
   - Лічильники (червоні значення, напр. `473 471`).
   - Іконка `Edit` (олівець) — постійно.
   - Іконка `Reset` — **тільки коли обрано `LIFETIME`**.
4. При вимкненому `Frequency Cap`:
   - Поле і кнопки неактивні (disabled state).
   - Поточні значення залишаються в state.
5. `Reset` у `LIFETIME`:
   - Скидає накопичений lifetime стан за офером (реалізація backend/API окремо).

## 8) UI/UX вимоги
1. Візуально зберегти існуючу структуру блоку зі скріншоту:
   - Card-контейнер.
   - Toggle + заголовок `Frequency Cap`.
   - Label `Global Cap`, input, праві індикатори.
   - Дві button-групи нижче.
2. Стилі для кнопок періодичності:
   - Active: синій фон/текст.
   - Inactive: сірий фон/текст.
3. `LIFETIME` має той самий стиль і розмір, що `DAILY/HOURLY`.

## 9) Логіка станів
### State matrix
- `enabled=false`:
  - input disabled
  - period/action buttons disabled
  - edit/reset disabled
- `enabled=true` + `period=daily/hourly`:
  - input active
  - edit visible
  - reset hidden
- `enabled=true` + `period=lifetime`:
  - input active
  - edit visible
  - reset visible

## 10) Acceptance criteria
1. У блоці `Frequency Cap` відображаються три режими: `DAILY`, `HOURLY`, `LIFETIME`.
2. Переключення на `LIFETIME` не ховає поле `Global Cap`.
3. Кнопка `LIFETIME` в активному стані стилістично відповідає іншим активним кнопкам.
4. Іконка `Reset` з’являється тільки в `LIFETIME`.
5. У не-LIFETIME режимах іконка `Reset` відсутня.
6. При `Frequency Cap = OFF` усі контроли блоку неактивні.

## 11) Тест-кейси (мінімальний набір)
1. Відкрити форму, увімкнути `Frequency Cap`, перевірити наявність `DAILY/HOURLY/LIFETIME`.
2. Обрати `LIFETIME`, перевірити:
   - input видимий;
   - reset visible;
   - edit visible.
3. Перемкнутися з `LIFETIME` на `DAILY`, перевірити що reset зникає.
4. Вимкнути `Frequency Cap`, перевірити disabled для всіх контролів.
5. Ввести невалідне значення в `Global Cap` (0, від’ємне, нечислове) — очікувати валідацію.

## 12) Ризики/залежності
- Потрібна узгоджена backend-логіка reset lifetime counter (idempotent, audit-friendly).
- Потрібно підтвердити точний рівень застосування капи (`Partner Offer Name`) у persistence/model.

2. Чи потрібен confirmation modal перед reset?
3. Чи потрібно логувати reset в audit trail з actor/timestamp?
